# 實驗：線上課側錄＋自動截圖的新流程（交接）

給新 session 的接手說明。先讀 `00_先讀我_知識總覽.md` 和 `skill/japanese-class-notes/SKILL.md`，再讀這份。

## 為什麼要做這個實驗

L33 只靠一份多語言逐字稿，日文辨識很差（「瓦利迪基」→ 割引），待確認清單 13 條大多是「辨識不清」。
實體教室錄影（老師在白板前走動、兩台設備時間不同、MTS 7 個 2GB 檔）評估後代價太大，**已放棄**。
改用另一堂**線上課**：側錄影片＋自動截圖，畫面是投影片，聲音乾淨。

## 素材

- 截圖：自動截圖，檔名帶電腦時鐘時間，例：`20261006_185516_253706_auto_05a54a41.png`
  ＝ 2026/10/06 18:55:16.253706。`auto` 是自動觸發（推測為畫面變化時）。
- 截圖和側錄是**同一台電腦**，時鐘一致。
- 影片被使用者裁成兩半過（為了塞進 Plaud），**不要假設影片有起始時間資訊**。
- 使用者已用 `tools/抽音軌.bat` 從**未切分的完整影片**抽出一整條音軌，給 Plaud 轉寫兩次：
  - 主要版：多語言（或中文）模式
  - 日文版：日文模式
- 兩份逐字稿都從同一條音軌來，時間軸相同。

## 流程

1. 經使用者同意後，用 Plaud MCP（`list_files`、`get_transcript`）讀兩份原始逐字稿。Plaud 的 AI 整理（下方提示詞）只當輔助。
2. **時間對齊**：逐字稿時間是「從音軌開頭起算」，截圖是電腦時鐘。找 2–3 個錨點（老師說「下一頁」或念出投影片標題的時刻）對照截圖時間，算出差值。差值一致就整堂套用；越後面差越多就線性修正。全部用程式算，只看錨點那幾張圖。
3. 每張截圖對應「這一頁停留期間」的逐字稿段落。換頁前後一兩句看內容決定歸屬（直播影音不同步通常 <1 秒，不影響）。
4. 接既有三階段流程（整理 → 撰寫 → 組版，每階段停下來等確認）。
5. 來源衝突的優先順序：截圖 ＞ 日文逐字稿 ＞ 多語言逐字稿 ＞ 上下文推斷。待確認清單的「依據」標出來源。
6. 主幹用多語言版（老師的中文講解），日文片段用時間重疊從日文版替換，不逐句硬配。

## 待使用者確認的事

- 這堂課的筆記格式要不要沿用原版講義的撰寫規則（可能是不同老師、不同教材）。
- 截圖是投影片／教材頁面嗎？要不要放進筆記（預設只當參考，不嵌入）。

## 成本規則（使用者在意）

- 未經同意不開子代理、不做大量處理。
- 截圖不要一次全看：先列檔名與時間，只看錨點和需要判讀的頁。必要時降解析度或 4 格拼一張。
- 影片原則上不需要；只有時間對不上時才用。

### 2026.10.11 更正：位置誤差的真正原因與複核

- 使用者回報「總是有幾秒誤差」。比對使用者 Drive 上的原始 m4a（環境網路加了 drive.google.com、drive.usercontent.google.com）：和 Plaud 音檔在 7 個時間點互相關偏移都是 0 ms、無漂移＝同一份錄音。誤差來自我的定位程式：
  1. 模型常把每段輸入的第一個 token 標在片段最開頭（例：色移り 的「い」標在 15 秒前）；加上漢字詞讀音跨 token 平均分配時間，把詞內空檔抹平（例：画面 標成 2.36 秒）。→ 讀音逐 token 取時間、頭尾孤立字（間隔 >1 秒）剔除、內部間隔 >1 秒（8 拍以下）或 >2 秒標「間隔異常」。
  2. 意思相近的不同版本（事前に「営業時間を」確認…）被當同一句，起點晚 1 秒。→ score ≥ 90 才可用。
  3. 短詞撞到不相干片段。→ 複核時必須逐字包含。
  4. 段末終點原本用片段結束或「最後有聲音處」，會被後面沒辨識出的聲音拖晚數秒。→ 改為往後找第一個停頓，最長 1.2 秒。
- `verify_clips.py`：從使用者的 m4a 切「起點前 0.6 秒～終點後 0.6 秒」重新辨識，只看文字判斷開頭／結尾是否在片段頭尾附近。靈敏度實測：正確位置 90% 通過，故意移動 ±1.2 秒只有約 15% 通過（多為同句在附近重複念）。
- 先前「起點最大 390 ms」只涵蓋前面有停頓的命中，漏掉上面的錯誤；那句結論作廢。用時間戳做的二次辨識一致性檢查（check_start_all.py）也受同一個假象影響，不能當判準。
